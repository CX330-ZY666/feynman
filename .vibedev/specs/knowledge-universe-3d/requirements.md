# 需求文档：knowledge-universe-3d

## 功能概述

本功能旨在构建一个基于 Three.js 的 3D 知识宇宙可视化系统，将用户的知识点数据以星球的形式在三维空间中展示，通过力导向布局算法实现自动排列，并支持自动和手动两种方式创建知识点之间的连接关系。用户可以通过鼠标交互探索知识图谱，直观地理解知识点之间的关联。

---

## 功能需求

### 1. 3D场景初始化与基础设置

**用户故事**：作为用户，我希望看到一个流畅的3D太空场景，以便在视觉上获得沉浸式体验。

**验收标准**：
1. WHEN 用户访问知识宇宙页面，THEN 系统应创建 Three.js 场景，包含透视相机、WebGL 渲染器和黑色太空背景
2. WHEN 场景初始化完成，THEN 系统应添加星空背景效果（至少 10000 个星点）
3. WHEN 场景渲染，THEN 系统应配置合适的光照系统（环境光 + 至少2个方向光/点光源）
4. WHEN 窗口大小改变，THEN 系统应自动调整相机宽高比和渲染器尺寸
5. WHEN 组件卸载，THEN 系统应正确清理所有 Three.js 资源（场景、渲染器、控制器）

---

### 2. 知识点数据获取与管理

**用户故事**：作为用户，我希望系统能自动加载我的所有知识点，以便在3D空间中可视化它们。

**验收标准**：
1. WHEN 页面加载，THEN 系统应通过 axios 调用 `/api/knowledge-points` 接口获取当前用户的所有知识点
2. WHEN API 调用成功，THEN 系统应将返回的数据存储在组件状态中
3. WHEN API 调用失败，THEN 系统应在控制台输出错误信息并显示友好的错误提示
4. WHEN 知识点数据为空，THEN 系统应显示"暂无知识点"的提示信息
5. WHEN 知识点数据加载完成，THEN 系统应触发3D场景的渲染逻辑

---

### 3. 数据驱动的3D节点渲染

**用户故事**：作为用户，我希望每个知识点都以独特的星球形式展示，以便直观地识别不同的知识点。

**验收标准**：
1. WHEN 知识点数据加载完成，THEN 系统应为每个知识点创建一个 3D 球体（SphereGeometry）
2. WHEN 创建球体，THEN 系统应使用 MeshStandardMaterial 材质，并赋予独特的纹理或颜色
3. WHEN 创建球体，THEN 系统应将知识点的元数据（id, title, content, category等）存储在球体的 userData 属性中
4. WHEN 创建球体，THEN 系统应为每个球体创建文字标签（Sprite），显示知识点标题
5. WHEN 球体数量超过 100 个，THEN 系统应采用性能优化策略（如 InstancedMesh 或减少几何体复杂度）

---

### 4. 力导向布局算法集成

**用户故事**：作为用户，我希望知识点能自动排列成有组织的结构，而不是杂乱无章地堆在一起。

**验收标准**：
1. WHEN 前端项目构建，THEN 系统应已安装 `d3-force-3d` npm 包
2. WHEN 节点创建完成，THEN 系统应初始化 d3-force-3d 模拟器，配置3D空间参数
3. WHEN 力模拟器初始化，THEN 系统应配置合适的力（排斥力 forceManyBody、中心力 forceCenter）
4. WHEN 动画循环执行，THEN 系统应调用 simulation.tick() 更新节点位置
5. WHEN 节点位置更新，THEN 系统应将计算出的坐标同步到 Three.js 球体的 position 属性
6. WHEN 力模拟达到平衡（alpha < 阈值），THEN 系统应停止不必要的计算以节省性能

---

### 5. 鼠标交互与节点高亮

**用户故事**：作为用户，我希望鼠标悬停在星球上时能高亮显示，以便知道我正在查看哪个知识点。

**验收标准**：
1. WHEN 用户移动鼠标，THEN 系统应使用 Raycaster 检测鼠标射线与球体的相交
2. WHEN 鼠标悬停在球体上，THEN 该球体应改变发光强度（emissiveIntensity）或颜色以实现高亮效果
3. WHEN 鼠标移开球体，THEN 球体应恢复原始的视觉效果
4. WHEN 球体被高亮，THEN 与该节点相连的所有连线也应同步高亮（改变颜色或透明度）
5. WHEN 鼠标移开，THEN 所有高亮效果应恢复到初始状态

---

### 6. 节点详情浮层显示

**用户故事**：作为用户，我希望点击星球后能看到详细信息，以便快速了解知识点内容。

**验收标准**：
1. WHEN 用户点击某个球体节点，THEN 系统应在页面右下角显示一个浮层面板
2. WHEN 浮层显示，THEN 面板应包含节点的标题（title）、分类（category）、标签（tags）和内容摘要（content前200字符）
3. WHEN 浮层显示，THEN 面板应提供"关闭"按钮或点击浮层外部可关闭
4. WHEN 用户点击空白区域，THEN 浮层应关闭并清空选中状态
5. WHEN 浮层显示，THEN 面板应有平滑的进入/退出动画效果

---

### 7. 自动连线系统

**用户故事**：作为用户，我希望系统能自动识别相关的知识点并连线，以便快速建立知识图谱的基础结构。

**验收标准**：
1. WHEN 节点渲染完成，THEN 系统应根据预定义规则自动生成连接关系数据
2. WHEN 生成规则为"相同category"，THEN 所有category字段值相同的节点之间应创建连线
3. WHEN 生成规则为"相同tag"，THEN 拥有至少一个相同tag的节点之间应创建连线
4. WHEN 连接关系数据生成，THEN 系统应使用 THREE.Line 或 THREE.LineSegments 渲染连线
5. WHEN 连线渲染，THEN 自动连线应使用特定颜色（如蓝色）以区别于手动连线
6. WHEN 连线数量过多（>500），THEN 系统应限制或优化连线显示以保证性能

---

### 8. 手动连线系统 - 拖拽创建

**用户故事**：作为用户，我希望通过拖拽的方式手动关联两个知识点，以便建立自定义的知识关系。

**验收标准**：
1. WHEN 用户进入编辑模式，THEN 系统应显示"编辑模式"指示器和相关操作提示
2. WHEN 用户在编辑模式下按住鼠标左键拖动某个球体，THEN 系统应显示一条跟随鼠标的临时连线
3. WHEN 临时连线拖到另一个球体上并释放鼠标，THEN 系统应创建一条新的连接关系
4. WHEN 创建新关系，THEN 系统应调用后端 API `POST /api/relations` 保存关系数据
5. WHEN API 调用成功，THEN 系统应在3D场景中渲染新的连线，并使用特定颜色（如黄色）标识为手动连线
6. WHEN API 调用失败，THEN 系统应撤销临时连线并显示错误提示
7. WHEN 用户尝试在已存在连线的两个节点间重复创建，THEN 系统应提示"关系已存在"

---

### 9. 连线删除功能

**用户故事**：作为用户，我希望能删除不需要的连接关系，以便保持知识图谱的准确性。

**验收标准**：
1. WHEN 用户在编辑模式下右键点击某条连线，THEN 系统应显示上下文菜单，包含"删除连线"选项
2. WHEN 用户选择"删除连线"，THEN 系统应弹出确认对话框
3. WHEN 用户确认删除，THEN 系统应调用后端 API `DELETE /api/relations/:id` 删除关系数据
4. WHEN API 调用成功，THEN 系统应从3D场景中移除该连线对象
5. WHEN API 调用失败，THEN 系统应保留连线并显示错误提示
6. WHEN 删除的是自动生成的连线，THEN 系统应将其标记为"已隐藏"而非物理删除

---

### 10. 编辑模式切换

**用户故事**：作为用户，我希望能在浏览模式和编辑模式之间切换，以便在不编辑时避免误操作。

**验收标准**：
1. WHEN 页面初始加载，THEN 系统应默认处于浏览模式
2. WHEN 页面显示，THEN 系统应提供明显的"进入编辑模式"按钮（位于右上角）
3. WHEN 用户点击"进入编辑模式"按钮，THEN 系统应切换到编辑模式并显示相关提示
4. WHEN 处于编辑模式，THEN 系统应启用拖拽连线、右键删除等编辑功能
5. WHEN 处于编辑模式，THEN 按钮文字应变为"退出编辑模式"
6. WHEN 用户点击"退出编辑模式"，THEN 系统应返回浏览模式并禁用编辑功能

---

### 11. 关系持久化 - 后端API

**用户故事**：作为开发者，我需要后端提供关系管理API，以便前端能够保存和获取知识点之间的关联。

**验收标准**：
1. WHEN 后端启动，THEN 系统应创建 `KnowledgeRelation` Mongoose 模型，包含字段：source, target, type, relationLabel, author, createdAt
2. WHEN 后端启动，THEN 系统应创建 `/api/relations` 路由文件
3. WHEN 前端调用 `POST /api/relations`，THEN 后端应验证用户身份、创建新关系记录并返回完整数据
4. WHEN 前端调用 `GET /api/relations`，THEN 后端应返回当前用户的所有关系记录
5. WHEN 前端调用 `DELETE /api/relations/:id`，THEN 后端应验证关系所有权并删除记录
6. WHEN 创建关系时source和target相同，THEN 后端应返回 400 错误"不能关联自己"
7. WHEN 创建重复关系，THEN 后端应返回 409 错误"关系已存在"

---

### 12. 知识图谱数据整合

**用户故事**：作为用户，我希望看到完整的知识图谱（包含自动和手动关系），而不需要手动合并数据。

**验收标准**：
1. WHEN 前端请求图谱数据，THEN 系统应提供统一的 API 接口返回节点和边数据
2. WHEN 后端处理请求，THEN 系统应自动计算自动关系（基于category/tag规则）
3. WHEN 后端处理请求，THEN 系统应从数据库查询手动关系
4. WHEN 后端返回数据，THEN 响应格式应为 `{ nodes: [...], links: [{ source, target, type, ... }] }`
5. WHEN links数组中包含type字段，THEN 'auto' 表示自动关系，'manual' 表示手动关系

---

### 13. 性能优化

**用户故事**：作为用户，我希望即使知识点很多时，3D场景仍能流畅运行，以便获得良好的使用体验。

**验收标准**：
1. WHEN 节点数量超过 50 个，THEN 系统应使用 requestAnimationFrame 优化动画循环
2. WHEN 连线数量超过 100 条，THEN 系统应考虑使用 THREE.BufferGeometry 批量渲染
3. WHEN 力模拟计算，THEN 系统应在模拟稳定后降低计算频率（如每5帧计算一次）
4. WHEN 鼠标交互检测，THEN 系统应使用防抖或节流优化 Raycaster 计算频率
5. WHEN 浏览器标签页不可见，THEN 系统应暂停动画循环以节省资源

---

### 14. 路由配置与导航

**用户故事**：作为用户，我希望能通过导航菜单访问知识宇宙页面，以便快速进入功能。

**验收标准**：
1. WHEN 前端路由配置，THEN App.jsx 应包含 `/knowledge-universe` 路由并映射到 KnowledgeUniversePage 组件
2. WHEN 用户访问该路由，THEN 系统应正确渲染知识宇宙页面
3. WHEN 导航栏组件，THEN 应添加"知识宇宙"菜单项并链接到 `/knowledge-universe`
4. WHEN 用户未登录，THEN 访问该路由应重定向到登录页
5. WHEN 路由切换离开该页面，THEN 系统应正确清理3D资源避免内存泄漏

---

### 15. 错误处理与边界情况

**用户故事**：作为用户，我希望系统能优雅地处理各种异常情况，而不会崩溃或显示难看的错误。

**验收标准**：
1. WHEN API 请求超时或网络错误，THEN 系统应显示友好的错误提示"网络连接失败，请稍后重试"
2. WHEN 知识点数据为空数组，THEN 系统应显示空状态提示"还没有知识点，快去创建吧！"
3. WHEN WebGL 不支持，THEN 系统应检测并显示"您的浏览器不支持 WebGL，请升级浏览器"
4. WHEN 节点数据缺少必要字段（如 _id），THEN 系统应跳过该节点并记录警告日志
5. WHEN 用户快速点击多次创建连线，THEN 系统应防止重复提交请求

---

## 非功能性需求

### 性能要求
- 场景帧率应保持在 30 FPS 以上（节点数 < 100 时应达到 60 FPS）
- 首次加载时间应小于 3 秒（不含 API 请求时间）

### 兼容性要求
- 支持 Chrome、Edge、Firefox、Safari 最新两个主要版本
- 需要支持 WebGL 1.0 或更高版本

### 可访问性要求
- 提供键盘快捷键（如按 E 切换编辑模式）
- 为交互元素提供合适的 aria-label

### 安全性要求
- 所有 API 调用必须携带有效的 JWT token
- 用户只能查看和编辑自己的知识点和关系数据
